# OCMake

OCMake lets you declare the dependencies of your OpenCore config.plist using just a `CMakeLists.txt`.

All you work on, and share, is a folder with as few as 5 files: 
`config.plist`, `CMakeLists.txt`, `ocmake.lock`, `secrets.plist`, and `secrets.plist.example`.

It handles OpenCore itself and its updates, ACPI, Kexts and their updates, and so on.

It does the fetching of the files on the your behalf, and automatizes 
ProperTree's Snapshot feature, so the files are automatically added to `config.plist`.
It also does a share of other things, **only** if you want it to.

It won't make choices for your build, or write the config.plist for you.
It just lets you automatize the (even more) boring tasks you would have done manually. 
Or skipped altogether like me, since, eh, your build already works who cares.

OCMake rewrites only the four sections that are derived from what is on
disk — `ACPI.Add`, `Kernel.Add`, `UEFI.Drivers`, `Misc.Tools` — plus whatever else that that is declared
explicitly using OCMake. Everything else in the plist is left alone.

**You are encouraged to follow the Dortania install guide as normal.**

Where does it differ from OCEBuild in practice?
I find the time wasted juggling around 10 different tools when quickly iterating on a new configuration
very annoying. OCMake lets you do everything from VSCode. Even installing the just modified EFI.

## Quick start

**New build (CLI)**
Modify/save as CMakeLists.txt
```cmake
cmake_minimum_required(VERSION 3.25)
project(my-hackintosh NONE)

include(FetchContent)
FetchContent_Declare(OCMake GIT_REPOSITORY https://github.com/NSCocoa/OCMake GIT_TAG main)
FetchContent_MakeAvailable(OCMake)
include(${ocmake_SOURCE_DIR}/OCMake.cmake)

oc_opencore(VERSION 1.0.8)
```
Run:
```bash
cmake --preset debug
```
It will fetch OpenCore and create a config.plist you can edit following the Dortania install guide.
Define all files suggested in 'Gathering Files' in the CMakeLists.txt instead of manually downloading them.

**Existing OCMake build**

```bash
git clone <your EFI repo> && cd <it>
cmake --workflow --preset release      # configure, build, validate
```

The EFI lands in `build/release/EFI`. Then:

```bash
cmake --install build/release --prefix /Volumes/USB   # -> /Volumes/USB/EFI/...
```

Copy `presets/CMakePresets.json` into your repo to get those presets (and a default
generator, so IDEs stop asking).

## Example usage:
```cmake
cmake_minimum_required(VERSION 3.25..4.4)
project(my-hackintosh NONE)
```
```cmake
include(FetchContent)
FetchContent_Declare(OCMake GIT_REPOSITORY https://github.com/CFCocoa/OCMake GIT_TAG main)
FetchContent_MakeAvailable(OCMake)
include(${ocmake_SOURCE_DIR}/OCMake.cmake)
```
Latest OpenCore:
```cmake
oc_opencore()
```

Latest, then pinned in the lock
```cmake
oc_kext(Lilu          GITHUB acidanthera/Lilu)
```

Or pin the version explicitly
```cmake
oc_kext(WhateverGreen GITHUB acidanthera/WhateverGreen VERSION 1.6)
```

Pick from a multi-kext archive
```cmake
oc_kext(VirtualSMC    GITHUB acidanthera/VirtualSMC
        KEXTS VirtualSMC SMCProcessor SMCSuperIO)
```

Use a local kext that is committed in the repository
```cmake
oc_kext(USBMap        PATH kexts/USBMap.kext)
```

Take an SSDT from OpenCore's decompiled samples, and have it compiled automatically
```cmake
oc_ssdt(SAMPLES SSDT-PLUG SSDT-EC-USBX)
```

Use a local prebuilt SSDT that is committed to the repository
```cmake
oc_acpi(acpi/SSDT-Vendor.aml)
```

Take Drivers from the OpenCore package
```cmake
oc_driver(OpenRuntime OpenCanopy)
```

From OcBinaryData
```cmake
oc_driver(OCBINARYDATA HfsPlus)
```

The resources that will be used by i.e. OpenCanopy (The GUI boot menu)
```cmake
oc_resources(IMAGE Acidanthera/Syrah)
```

Tools from the OpenCore package:
```cmake
oc_tool(OpenShell)
```

Generate the files necessary for OpenCore's Vault feature to work, in Basic mode
```cmake
oc_vault(BASIC Release)
```

The serial number and other values generated by GenSMBIOS are intentionally separated
in a `secrets.plist` file you should add to .gitignore.

`config.plist` and `secrets.plist` are picked up by name — see [Defaults](#defaults).

## Features

- **Automatically fetch OpenCore and generate a config.plist**

- **No 35 MB of binaries in your repo.** Name a kext and it tracks upstream's latest
  release; the archive is downloaded
  once into a shared cache and pinned by hash in `ocmake.lock`. Committing that lockfile
  makes the build reproducible and, with a warm cache, entirely offline.
- **Release/Debug is one flag.** `-DCMAKE_BUILD_TYPE=Debug` switches OpenCore, every kext
  and every driver to their DEBUG builds *and* applies the usual debug `config.plist`
  knobs. Both build directories can coexist.
- **One build step for everything.** `.dsl` files are compiled with `iasl`, the tree is
  staged, `config.plist` is assembled — no manual ProperTree snapshot, no dragging files
  into `EFI/OC/ACPI`.
- **It checks its own work.** `ctest` runs `ocvalidate` (version-matched, out of the same
  OpenCore package you are staging) plus checks for missing files, kext load order,
  duplicate bundle identifiers and impossible kernel ranges.
- **It tells you what it built.** Every build writes a `BOM.md` listing every artefact and
  where it came from, with links.

## Commands

| Command | What it does |
|---|---|
| `cmake --build build` | Stage the EFI into `build/EFI` |
| `ctest --test-dir build` | `ocvalidate` + OCMake's own checks |
| `cmake --build build --target report` | Print the bill of materials |
| `cmake --build build --target diff-esp` | Show what installing would change on the ESP |
| `cmake --build build --target install-esp` | Back up the ESP's EFI, then install |
| `cmake --build build --target outdated` | Table of pinned versus latest upstream versions |
| `cmake --install build --prefix /Volumes/USB` | Drop-in copy to a USB stick |
| `cpack --config build/CPackConfig.cmake` | Zip the EFI for a release |

`--component <name>` is required when a project builds more than one EFI.

With more than one `oc_efi()` in a project, each target also exists suffixed: `validate-<name>`.

## API

### Packages

```cmake
oc_opencore([VERSION <x.y.z|latest>] [BUILD RELEASE|DEBUG] [ASSET <glob>]
            [URL <url> [SHA256 <hash>]] [EFI <name>])
```
The OpenCore release everything else is staged against. Required. **`VERSION` defaults to
`latest`** — whatever that resolves to is pinned in `ocmake.lock`, so the build stays
reproducible and `-DOC_UPDATE=ON` is what moves it.

```cmake
oc_kext(<name> [GITHUB <owner/repo> VERSION <v>] [BUILD RELEASE|DEBUG] [ASSET <glob>]
        [URL <url> [SHA256 <hash>]] [PATH <local .kext or dir>] [KEXTS <a> <b> ...]
        [MIN_KERNEL <v>] [MAX_KERNEL <v>] [ARCH <a>] [ENABLED <ON|OFF>] [COMMENT <s>]
        [EFI <name>])
```
One kext package; needs one of `GITHUB`, `DORTANIA`, `URL` or `PATH`. `DORTANIA` takes the
build [Dortania](https://dortania.github.io/build-repo/) publishes for every upstream
commit — where you go for a fix that is merged but unreleased, or for a DEBUG build of a
project whose own releases ship none. The index carries a published SHA-256, so the lock
records a digest the publisher asserted rather than one OCMake merely observed. `<name>` is the declaration's own
name and its lockfile key, not necessarily a bundle name. **`VERSION` defaults to `latest`**,
same as `oc_opencore()`. `KEXTS` selects which bundles to take from an archive that
ships several; without it, all of them are staged. `MIN_KERNEL` … `COMMENT` are written
onto that bundle's `Kernel.Add` entry.

Kexts with no DEBUG asset fall back to RELEASE automatically, and say so.

### ACPI

```cmake
oc_ssdt(<file.dsl> ... [SAMPLES <name> ...] [FLAGS <iasl flags>] [EFI <name>])
oc_acpi(<file.aml> ... [EFI <name>])
```
`oc_ssdt()` compiles with `iasl`, which is found on `PATH` or fetched (a pinned MaciASL
build on macOS, open-acpica on Windows; on Linux install `acpica-tools`). `SAMPLES` takes
tables straight out of the OpenCore package's `Docs/AcpiSamples/Source`, so a table you do
not intend to edit needs no copy in your repo. `oc_acpi()` stages prebuilt `.aml`.

### Drivers, tools and resources

```cmake
oc_driver([<name> ...] [OCBINARYDATA <name> ... [REF <ref>]] [URL <url> [SHA256 <hash>]]
          [PATH <file.efi> ...] [EFI <name>])
oc_tool([<name> ...] [URL <url> [SHA256 <hash>]] [PATH <file.efi> ...] [EFI <name>])
```
Bare names come from the OpenCore package. `OCBINARYDATA` fetches from
`acidanthera/OcBinaryData` — where `HfsPlus.efi` lives, since OpenCorePkg cannot
redistribute Apple's driver — pinned to a commit. One call may mix all four sources.

```cmake
oc_resources([OCBINARYDATA] [FONT ON|OFF] [LABEL ON|OFF] [AUDIO ON|OFF]
             [IMAGE ON|OFF|<set>] [REF <ref>] [URL <archive> [SHA256 <hash>]] [EFI <name>])
```
The picker's `OC/Resources`. Defaults to FONT, LABEL and IMAGE; AUDIO is opt-in because it
is 6.3 MB of `.wav` that only `UEFI/Audio` reads. Naming an icon set —
`IMAGE Acidanthera/GoldenGate` — stages that set alone and writes `Misc/Boot/PickerVariant`
to match, so the theme is stated once.

### config.plist

```cmake
oc_config(<config.plist> [EFI <name>])
oc_config_overlay(<fragment.plist> [CONFIG <type>] [EFI <name>])
oc_config_set(<keypath> <STRING|INTEGER|BOOL|DATA|REAL> <value> [CONFIG <type>] [EFI <name>])
oc_boot_args([APPEND <arg> ...] [REMOVE <arg> ...] [CONFIG <type>] [EFI <name>])
oc_secrets(<plist> [OPTIONAL] [EFI <name>])
```
Keypaths are `/`-separated, because NVRAM GUIDs contain dashes: `Misc/Debug/Target`,
`NVRAM/Add/7C436110-AB2A-4BBB-A880-FE41995C9F82/boot-args`. Numeric components index
arrays. `CONFIG Debug` limits a declaration to one build variant. Overlays deep-merge.
`oc_boot_args()` edits the string in place, replacing by key, so `debug=0x100` supersedes
an existing `debug=…` rather than duplicating it.

`oc_secrets()` is merged last, after everything else, so machine identifiers
(`PlatformInfo/Generic/*`) never have to live in the committed `config.plist`.

**You do not need to write the first `config.plist` yourself.** If the file a project declares is
not on disk, OCMake creates it from the OpenCore package's own `Docs/Sample.plist`, with
`ACPI/Add`, `Kernel/Add`, `UEFI/Drivers` and `Misc/Tools` emptied — those four are derived
from what you declare. Everything else, `#WARNING` keys included, is kept. It is announced,
and from then on the file is yours:

```
-- OCMake: created config.plist from OpenCore 1.0.7's Docs/Sample.plist -- hand-written from here on, so commit it
```

A `config.plist` that already exists is never touched: it is yours, and it is merged into.
That is the whole rule — no detection, no marker. It matters because OCSnapshot *merges*,
so a raw Sample.plist copy would let the sample's own entries (one is a **disabled**
`VoodooPS2Controller`) outrank what you declare. Creating the file cleaned means an OCMake
project never contains a raw sample. `oc_config(<file> CLEAN)` rebuilds all four sections
on every build, for migrating a config that was copied from the sample by hand.

### Vaulting

```cmake
oc_vault(<BASIC|SECUREBOOT> [<Release|Debug|All>] [EFI <name>])
```

| | What it writes | What it buys |
|---|---|---|
| `BASIC` | `vault.plist` | OpenCore checks every file it loads against a SHA-256 manifest. The manifest is unauthenticated, so this catches a half-copied tree or a stale file — not an attacker, who would regenerate it. |
| `SECUREBOOT` | `vault.plist`, `vault.sig`, and the public key embedded in `OpenCore.efi` | The manifest can no longer be swapped without also replacing the binary that verifies it. |

`SECUREBOOT` rather than OpenCore's own name for it, because the name should say what it
needs: the chain terminates at `OpenCore.efi`, and only firmware **UEFI Secure Boot**
verifies that. Without it, an attacker replaces `OpenCore.efi` with one carrying their own
key. This raises the cost of tampering; it is not a boundary on its own.

The second argument says which variants to vault and defaults to `All` — vaulting only
Release would quietly leave a Debug build unprotected, and plenty of people run Debug daily.
Out of scope means no manifest *and* no `Vault` key claiming there is one.

The manifest is rebuilt whenever anything staged changes, and `ctest` recomputes it, so a
tree that has drifted is caught before the machine stops at the picker.

`BASIC` needs nothing but Python. `SECUREBOOT` needs
[pyca/cryptography](https://github.com/pyca/cryptography) for key generation and signing;
if it is not already importable, OCMake creates a small environment for it under
`OC_CACHE_DIR`, once per machine, shared across projects. Point `OC_PYTHON_ENV` at an
environment you manage instead, or install the package yourself and OCMake will just use
it. All three platforms are supported.

**OCMake never relaxes `Misc/Security/Vault` for you.** OpenCore's `Docs/Sample.plist` ships
`Secure`, and a scaffolded config keeps it — if you do not vault and do not change it, it
breaks exactly as it would have without OCMake. `occheck` tells you which it is.

### Several EFIs in one repo

`oc_efi(<name>)` names the EFI that the declarations after it belong to, for the rest of
the enclosing scope — one directory per machine, or as section markers in a flat file:

```cmake
oc_efi(desktop)
oc_opencore()
oc_kext(Lilu GITHUB acidanthera/Lilu)
```

`EFI <name>` on an individual declaration always wins over that, which is what lets one
loop declare the same kexts for several machines:

```cmake
foreach(machine IN LISTS MACHINES)
  oc_kext(Lilu GITHUB acidanthera/Lilu EFI ${machine})
endforeach()
```

Each gets `build/<name>/EFI` and its own `efi-<name>`, `validate-<name>`, `report-<name>`
targets. The bare aliases and the CPack target exist only when there is exactly one EFI,
because with several there is nothing sensible for them to mean. Install one at a time —
they all target `<prefix>/EFI`, so installing together is refused rather than silently
mixed:

```bash
cmake --install build --component desktop --prefix /Volumes/USB
```

### Finalizing

```cmake
oc_efi([<name>] [OUTPUT_DIR <dir>])
```
Names the EFI that the declarations after it belong to, for the rest of the enclosing
scope, and optionally moves its output. Optional and position-independent: finalization is
deferred either way, and a single-EFI project needs no call at all.

### Defaults

These are applied unless you say otherwise, and are listed in `OCMake.cmake` as
`OC_DEFAULT_*` variables you can change:

| | |
|---|---|
| `config.plist` | used as the base if you call no `oc_config()` |
| `secrets.plist` | used if present; **required** if a `secrets.plist.example` sits beside it |
| `Misc/Debug/Target 67`, `Misc/Debug/AppleDebug true` | Debug builds only |
| `boot-args += -v debug=0x100 keepsyms=1` | Debug builds only |

An explicit declaration always wins. `-DOC_DEFAULTS=OFF` disables the lot.

### Knobs

| Variable | Default | Meaning |
|---|---|---|
| `OC_BUILD` | follows `CMAKE_BUILD_TYPE` | Force `RELEASE` or `DEBUG` |
| `OC_UPDATE` | `OFF` | Re-resolve everything, ignoring `ocmake.lock` |
| `OC_OFFLINE` | `OFF` | Never touch the network; fail if the lock or cache is cold |
| `OC_CACHE_DIR` | `~/.cache/ocmake` | Shared download cache |
| `OC_ESP` | auto-detected | Where `install-esp` writes |
| `OC_ESP_BACKUP` | `ON` | Archive the ESP's EFI before replacing it |
| `OC_PACKAGE` | `ON` | Register the CPack zip target |
| `OC_DEFAULTS` | `ON` | Apply the built-in defaults |
| `OC_PYTHON_ENV` | managed in `OC_CACHE_DIR` | Python environment for scripts needing third-party packages |

## How it works

Resolution and fetching happen at **configure** time, so archives are on disk and can be
globbed while build rules are generated. Staging, `iasl`, and `config.plist` assembly
happen at **build** time, incrementally.

`ocmake.lock` records, for every declaration, the version it resolved to, the exact asset
URL and its SHA-256. **Commit it.** With the lock present no GitHub API call is made at
all, so a clean clone plus a warm cache builds with `-DOC_OFFLINE=ON`. `-DOC_UPDATE=ON`
re-resolves and rewrites it. Because the lock pins the URL and hash, checking out an older
lock and rebuilding reproduces that EFI byte for byte — which is also your rollback story.

`config.plist` is assembled as: your base → declared overlays and sets → OCSnapshot (the
same tool ProperTree drives, vendored here) → per-kext overrides → `secrets.plist`.

## CI

A reusable workflow is included:

```yaml
jobs:
  efi:
    uses: NSCocoa/OCMake/.github/workflows/build-efi.yml@main
```

It builds, validates, checks that `ocmake.lock` did not move, and uploads the EFI as a zip.

## Requirements

CMake 3.25+, Python 3.9+ (standard library only), and `iasl` if you compile `.dsl` files.
`iasl` is fetched automatically depending on your system, so you don't need to do it.
